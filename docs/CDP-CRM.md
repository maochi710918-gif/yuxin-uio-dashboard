# 裕信 UIO：CDP 客戶資料平台 ＋ CRM 商機管理 ＋ 銷售與售後協作

平台只處理**地端已編碼、已遮罩**的資料；身分對照與實際聯絡在地端完成。平台不建立身分對照表，也沒有任何直接識別資料的欄位或查詢功能。

## 核心流程

| # | 步驟 | 平台功能 |
|---|---|---|
| 1 | 地端整理資料、產生穩定編碼 | `data-pipeline/export_entities.py`（UIO 活頁簿 → 各實體 CSV）、`csi_to_platform.py`（CSI 車牌 → 車輛編碼） |
| 2 | 匯入平台 | 資料管理 → 資料匯入（欄位對照 → 檢查 → 預覽 → 確認）；或 `scripts/import-entities.mjs` |
| 3 | 串接、建立輪廓／客群／商機 | 客戶 360、客群（AND/OR/NOT）、評分、自動化規則 |
| 4 | 篩選名單、分派、下載 | 客群 → 建立任務／活動快照；任務 → 匯出（批次編號＋名單版本） |
| 5 | 地端比對並執行 | 匯出檔只有編碼；地端以「還原個資」工具或自有流程比對 |
| 6 | 以相同編碼回傳 | 任務 → 結果回傳（依任務編碼回寫，並核對客戶／商機編碼） |
| 7 | 更新任務、商機與成效 | 任務狀態、商機漏斗、主管儀表板、互動時間軸 |

## 資料模型（D1／SQLite，`db/migrations/`）

- **客戶** `customers`、**車輛** `vehicles`、**家庭／企業** `relation_groups` + `relation_group_members`
- **人車關係** `vehicle_relations`（持有人／使用人／付款人／決策者，`valid_from`／`valid_to`；轉手時舊關係補結束日，不刪除）
- **負責人員** `vehicle_staff`（業代／服專／技師，同樣保留期間）
- **交易** `transactions`（合併後）＋ `transaction_source_records`（各來源原始紀錄）
- **互動** `interactions`、**滿意度** `satisfaction_surveys`
- **商機** `opportunities` ＋ `opportunity_events`（每次異動）
- **任務** `tasks` ＋ `task_events`；**匯出** `export_batches`；**回傳** `result_batches` ＋ `result_rows`
- **客群** `segments`（動態，隨資料更新）、**活動** `campaigns` ＋ `campaign_members`（產生當下的快照）
- **據點與人員** `units`、`staff`；**使用者與權限** `app_users`、`user_impersonation`
- **匯入** `sources`、`import_batches`、`import_staging`、`import_errors`；**稽核** `audit_log`；**設定** `app_settings`
- **運算快取** `seg_snapshot`（客群基底，資料版本或分析基準日變更時自動重建；可隨時刪除）

所有編碼皆為 TEXT（保留前導零）。缺值存 NULL，畫面顯示「資料不足」；從未匯入的來源顯示「尚未串接」。

### 去重與衝突規則
- 主鍵為穩定編碼；交易以「來源＋來源紀錄 ID」判斷重複，不以遮罩後的文字判定同一人。
- 同檔內鍵值重複 → 該列失敗（`duplicate_in_file`）。同檔再匯入 → 全部「無變更」，並提示與既有批次相同。
- 欄位衝突：空白不覆蓋既有值；兩邊都有值時，**來源優先順序數字小者勝**，同優先時**資料日期新者勝**。
- 交易合併：每個欄位取優先順序最高且有值的來源（例：金額取維修工單、成本取消費明細）。

## 遷移與回復

- 啟動時自動依序套用 `db/migrations/NNNN_*.sql`，紀錄於 `_migrations`。
- 回復：依相反順序執行 `NNNN_*.down.sql`（例：`0003_satisfaction.down.sql` → `0002` → `0001`）。`0001` 會刪除全部 CRM 資料表，請先匯出。
- 分析資料來源：已有匯入車輛時，總覽／客戶查詢／金三角改由資料庫產生；資料庫無車輛時退回舊版 `public/data/vehicles.json` 快照（介面會顯示資料來源）。
- 本機資料庫位於 `.wrangler/state/`；備份即複製該資料夾。

## 角色與權限（後端判定）

| 角色 | 可見範圍 |
|---|---|
| 公司主管 | 全部；可管理匯入、使用者、設定；可「以此身分檢視」驗證權限（伺服器保存並記錄稽核） |
| 據點主管 | 所屬單位的車輛、任務、商機；可建立客群任務與執行自動化 |
| 業務（銷售顧問） | 指派給自己的車輛（`vehicle_staff` 業代）、自己負責的任務與商機 |
| 服務顧問 | 指派給自己的車輛（服專）、自己負責的任務與商機 |

身分來自登入（`oai-authenticated-user-*`），網址的 `view`／`role` 只切換畫面，不影響資料範圍。第一位登入者自動成為公司主管。

## 規則（可解釋、有版本）

- **保固**：預設 3 年或 10 萬 km 先到者；同時檢查時間與里程；最新里程缺漏 → 「待確認」，不依車齡推定仍在保固內。
- **評分 v1（2026-10-07）**：客戶價值、互動熱度、換購線索、流失風險；每條規則顯示欄位、分數與依據；資料不足不輸出分數；可人工修正並記錄原因。車齡與維修金額只作為「線索」。
- **下一步建議**：每筆含建議行動、判斷依據、待確認資訊、負責人與期限；標示「規則建議（非 AI 預測）」。
- **自動化**：觸發 → 排除（不可聯絡／拒收 → 客訴暫停促銷 → 停止條件 → 頻率控管 → 重複任務）→ 建立任務 →（地端執行、回傳）→ 後續或停止。規則修改產生新版本，任務記錄建立時的版本；執行（含試算）都有紀錄。目前為手動觸發，排程需平台 Cron。
- **任務狀態**：待處理 → 待匯出 → 已匯出 → 待回傳（未接通等非最終結果）→ 已完成／已取消。「已匯出」不代表已聯絡。
- **營收**：只計入成交商機所連結的實際交易編碼；商機狀態本身不產生營收。
- **歸因**：成交只歸屬於產生或推進該商機的任務所屬活動，不重複計入；無對照組，標示為「關聯成效」。
- **指標口徑**：名單成效依任務分派月份；營運結果依交易發生月份；每個指標附定義、分母、日期口徑、來源與下鑽。

## 驗收

`node scripts/verify-crm.mjs` 以 `ZZTEST-` 測試資料（`TEST-` 來源）實際走完 14 項驗收，結束後清除測試資料。
